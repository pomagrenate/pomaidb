## 1. Purpose & Architecture

Debugging memory allocator failures, subtle heap corruptions, and race conditions is notoriously difficult because timing variations and non-deterministic address space layout randomization (ASLR) can mask reproduction.

The `palloc_replay` utility provides a **100% deterministic replay environment**. It allows QA engineers, systems developers, and CI pipelines to:
1. Re-execute identical allocation sequences given an integer seed.
2. Replay recorded operation logs from failing test sessions or crash dumps.
3. Validate memory integrity continuously using front/back poison red-zones and interval-tree disjointness checks via `AllocatorOracle`.

---

## 2. Command-Line Syntax & Usage Modes

The `palloc_replay` executable operates in two primary modes: **Deterministic Seed Mode** and **Trace Log Replay Mode**.

### 2.1 Deterministic Seed Mode

Replays an exact pseudo-random sequence generated by the Mersenne Twister (`std::mt19937_64`) engine:

```bash
# Syntax:
./build/tests/palloc/palloc_replay <seed> [operation_count]

# Examples:
# Replay 50,000 ops with seed 1337:
./build/tests/palloc/palloc_replay 1337

# Replay 1,000,000 ops with seed 0xDEADBEEF (3735928559):
./build/tests/palloc/palloc_replay 3735928559 1000000

# Replay extinction test seed 2026:
./build/tests/palloc/palloc_replay 2026 500000
```

#### Behavior in Seed Mode:
- Generates allocations ranging from 16 bytes to 8,192 bytes with 64-byte AVX-512 alignment.
- Mixes 50% allocation actions with 50% randomized deallocation actions.
- Automatically initializes payload bytes and guards with PRNG patterns.
- Frees all residual live blocks at the end of the run, asserting zero leaks.

---

### 2.2 Trace Log Replay Mode

Replays an explicit sequence of memory operations recorded from a trace file:

```bash
# Syntax:
./build/tests/palloc/palloc_replay --file <path_to_trace_log>

# Example:
./build/tests/palloc/palloc_replay --file crash_trace.log
```

#### Log File Syntax
Trace files are plain text lines containing whitespace-delimited instructions. Empty lines and lines starting with `#` are treated as comments:

```text
# Trace Log: Vector Ingestion Sequence
ALLOC 512 64
ALLOC 1024 64
ALLOC 2048 64
FREE
ALLOC 4096 64
FREE
FREE
FREE
```

- `ALLOC <size_bytes> <alignment_bytes>`: Allocates a buffer of the specified size and alignment, registering it with the oracle.
- `FREE`: Deallocates the most recent live block, validating that red-zones have not been corrupted.

## 3. Invariant Checking Under Replay

Throughout the replay process, every allocation is wrapped and tracked by `pomai::palloc_qa::AllocatorOracle`:
- **Disjoint Intervals**: The binary search interval tree asserts that the newly allocated memory span $[P, P + \text{usable})$ does not intersect with any other live allocation.
- **Underflow Detection**: The 32-byte front canary (`0xA5 ^ (seed & 0xFF)`) is verified upon deallocation.
- **Overflow Detection**: The 32-byte back canary (`0xA5 ^ (seed & 0xFF)`) is verified upon deallocation.
- **Leak Detection**: If any allocation remains unfreed upon process exit, the oracle outputs diagnostic stderr alerts detailing leaked pointer addresses and sizes.

## 4. Debugging a Failing Replay with GDB / WinDbg

When an assertion or memory corruption triggers during a replay, run `palloc_replay` under a debugger to pinpoint the root cause:

### Using GDB (MinGW):
```bash
gdb --args ./build/tests/palloc/palloc_replay 1337 100000
(gdb) catch throw
(gdb) run
# Upon exception:
(gdb) bt
(gdb) print oracle.live_intervals_
```

### Using WinDbg / CDB (Windows Native):
```cmd
cdb.exe -g -G ./build/tests/palloc/palloc_replay.exe 1337 100000
```
